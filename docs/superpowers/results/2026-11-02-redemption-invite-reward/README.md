# 兑换码邀请比例返奖

日期：2026-11-02（Asia/Tokyo）。用户要求确认兑换码是否触发邀请返奖，不生效则补齐。检查确认原 Redeem 只做额度/订阅履约及邀请金额统计，不调用邀请比例返奖。

## 规则与实现

- 使用既有 InviteRewardMode、InviteRewardRatio 和邀请方个人 invite_reward_ratio；仅比例模式返奖，个人比例优先且显式 0 禁用；固定注册奖励模式保持不额外返奖。不新增参数，不自动开启返奖或开放金额查看权限。
- 钱包额度码：兑换授予额度 × 比例，精确十进制计算，沿用向零取整到整数额度的规则。订阅兑换码：使用本次实际创建的订阅 AmountTotal；不按套餐标价、不按不适用的兑换码 Quota 字段，也不累计未来每日重置次数。无限额/没有正数额度的套餐不凭标价补造返奖金额。
- 奖励计入邀请方待使用收益 aff_quota 和历史收益 aff_history，保留原钱包余额和邀请人数。无邀请人、自邀、已删除或停用的邀请方不新增奖励。只对后续成功兑换生效，不追溯补发历史已用码。
- 使用 GORM clause.Locking 锁兑换码行；兑换履约、奖励写入、兑换码已用标记同属一个事务。余额/历史收益溢出或奖励写入失败时全部回退，兑换码保持可重试；重复/并发兑换只有一个成功提交。日志在提交后写入，仅含兑换码 ID，不记录完整码。
- 新函数位于 model/redemption_reward.go；Redeem 调用它。无新增表或数据库迁移。既有邀请金额报告快照继续独立记录，不参与控制履约成功与否。
- 后台“邀请奖励模式”说明已更新全部 7 种语言。启用入口：系统设置 → 运营设置 → 额度设置 → 邀请奖励模式选择“比例返奖”，填写默认比例或使用个人比例。

## 验证

- 先观察旧实现失败：钱包/订阅缺少奖励、全局/个人比例不生效、错误注入未导致事务回退；修复后通过。
- SQLite 覆盖额度及小数取整、订阅授予额度、无限额、个人/零比例、固定模式、无邀请/自邀/停用邀请方、过期/已用/缺套餐、奖励写入失败后的钱包与订阅整体回退、重试、两个收益字段各自溢出及并发防重。
- PostgreSQL 16、MySQL 8 实测：同码 8 次并发只有 1 次成功，入账 500001、奖励 125000，快照仅 1 条；不同受邀人用不同码并发奖励同一邀请人，8 次均成功，每次 25，共增加 200，未丢失更新。隔离测试 DSN 强制只允许本机 invitation_test 库。完成后把本轮启动的本地专用数据库容器恢复为停止状态。

- Bun 63 项通过，7 种语言新文案存在，前端生产构建和 Go 静态程序构建通过；保留既有大包构建提示。
