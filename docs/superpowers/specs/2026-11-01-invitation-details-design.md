# 邀请名单与金额可见范围设计

日期：2026-11-01（Asia/Tokyo）。状态：用户已确认（2026-11-01）；实现和验证状态见结果报告，本设计不代表已发布生产。

用户后续修订（2026-11-02）：名单仅展示用户名和累计总金额，去除分项、折算依据和历史明细；自动更新采用当前页静默查询及变化行合并，保留阅读位置。该要求覆盖本文旧版展示细节，见 `docs/superpowers/results/2026-11-02-invitation-refresh/README.md`。

## 目标与已确认需求

钱包管理 → 邀请奖励中的“邀请人数”成为可点击入口，查看当前登录用户直接邀请的用户的用户名。本文将查看名单的人称为“邀请方”，名单中的人称为“受邀用户”，不查询邀请方的上级邀请人，也不递归统计间接邀请。

用户已确认：

1. 默认只展示用户名，不展示受邀用户的充值等金额。
2. 后台采用方案 A，统一设置“关闭／全部邀请方／指定用户”三个金额可见范围。
3. 金额包括充值、兑换码及订阅购买；充值和订阅使用实际支付金额，兑换码按额度折算金额。

金额可见权限授予的是**查看自己名单的邀请方**，不是向被选择的受邀用户公开其他人的数据。“指定用户”以搜索用户名选择用户，持久化稳定用户 ID；改用户名不改变授权。

## 方案选择

### A：统一后台配置（用户已选择）

一个参数同时保存模式和用户 ID 名单，例如 `mode=off|all|selected`、`user_ids=[...]`，作为一次 option 更新校验、保存与发布，避免先开放模式后保存名单的中间状态。默认 off；selected 且名单为空不开放。非法模式/名单应拒绝保存，运行时遇到缺失或损坏配置按 off 处理。

优点：符合现有邀请参数入口，可以统一关闭；便于核对哪些邀请方有权限。代价：需要后台用户名搜索和已选用户回显。

### B：用户管理逐个授权（已放弃）

在用户编辑表单加标记，适合独立维护每人权限，但不便统一收回，不符合已选的集中配置方式。

不采用纯前端隐藏金额：接口仍会泄露受邀用户信息，无法满足实际权限要求。

## 名单与后台交互

以下为设计者建议，尚不是用户对布局细节的逐项指定：

- 点击邀请人数打开分页名单弹窗，默认每页 20，最大 100，支持按用户名筛选。0 人也能打开并显示空状态；加载、失败和重试状态明确。
- 默认列表只显示用户名；授权时增加“充值实付”“订阅实付”“兑换折算”“合计”栏目。实付与折算明确区分，金额按币种分别列出，不把 USD、CNY 等直接相加。
- 无权限响应中金额字段和金额汇总均不存在，不用 0 假装隐藏；前端不提前请求金额专用数据。搜索和分页继续服从同一权限。
- 配置改动后，下次请求立即按新权限执行；刷新或请求失败时不沿用旧的敏感金额列表。账号切换、切换列表和权限关闭均清理已展示金额。
- 后台在现有邀请参数区域增加模式选择和多用户搜索选择器。关闭或全部模式下保留已选名单用于以后切回，但它不授予额外权限。保存结果必须以接口 success 为准，不能 HTTP 200 就显示成功。
- 后台用户选择结果只提供 ID/用户名等必要选项，不引入面向普通用户的全站用户搜索。
- 名单排除已删除用户，用户名跟随现有用户可见/删除语义，不泄露注销账户的历史身份。aff_count 保持现有累计邀请计数，不为本功能重算或回写；名单分页总数表示当前可查看的直接受邀用户数，两者可能因注销不同。

## 金额统计规则

只统计属于当前受邀用户的成功/已兑换记录，按用户 ID 关联；不按可变用户名关联。采用精确十进制金额计算与字符串金额 DTO，禁止浮点逐项累加后制造小数误差。展示与四舍五入遵从币种小数位规则。免费订单的有效实付 0 必须与未知金额区分。

### 充值

- 成功在线充值及已有管理员充值均计入；失败、待支付、过期订单不计入。
- 新记录保存可用于报告的实付金额、币种、完成时间及来源依据。能从通过校验的网关支付成功结果取得实付的，以该结果为准；不得用用户提交金额或未验签回调更新统计。
- 报告快照独立于现有入账/返奖金额，不能为了展示改写旧 Money、用户余额、返奖、批处理或幂等行为。
- 管理员直接充值使用其已确认的充值金额，按该操作的现有业务计价单位记录，并标注“管理员充值”；不将它伪称为银行卡/第三方扣款。

### 订阅购买与去重

- 成功 subscription_orders 为订阅购买的权威来源。相同交易号的充值镜像从充值金额排除，一个订阅订单只计算一次。
- 新订单的实付/币种快照优先来自经校验的支付完成信息；已有可靠 provider payload 可用于读取历史实付，但只解析服务端已保存的成功记录。
- 无法确认实际扣款时不以当前套餐价格替代原订单支付金额。
- 不将订阅授予额度另计为现金；付费订阅与兑换码授予的订阅分别按实际来源统计。

### 兑换码

- 只统计 status=used 且 used_user_id 为受邀用户的实际兑换；兑换码创建人、未使用码、过期未兑换码不计入。
- 额度兑换码：使用该次已兑入的额度。折算基准为 `额度 / QuotaPerUnit` 得到等值 USD，再按站点展示币种的汇率折算；报告明确注明采用的基准与汇率，不称为已核验现金付款。
- 新兑换记录保存当次额度、换算基准、币种、汇率和折算金额快照，未来修改 QuotaPerUnit 或汇率不重写历史快照。旧记录无快照时可以使用当前配置折算，必须标注“按当前配置估算”，不能与有历史依据的快照混淆。
- 订阅类型兑换码使用其实际授予的 user_subscription.amount_total 折算，不同时增加订阅实付。无限额度（amount_total=0）或无法恢复授予额度时显示“无法按额度折算”及记录数，不捏造金额或静默当成已支付 0。
- 一次兑换只计算一次；重试、支付回调重复、订阅充值镜像不能增加统计金额。

### 历史不足与合计

- 新增用于报告的可空金额/币种/依据快照字段或等价独立快照记录，采用三种数据库兼容的 GORM 迁移；具体最小存储实现由实施者选择，但不能改变既有财务字段含义。
- 确认成功但缺失可靠实付或币种的旧订单，保留“历史记录金额（实付/币种未确认）”及条数，不能直接纳入已确认实付合计，不能通过当前支付设置猜测历史币种。未知金额不是 0。
- 同一币种合计为已确认充值实付 + 已确认订阅实付 + 可折算兑换金额；提供来源分项及估算/缺失标识。不同币种分别展示合计，不新增后台汇率参数或外部汇率请求来制造单一总额。
- 本功能没有退款台账与原始支付记录的可靠全量映射，统计的是现有成功支付的累计记录额，不承诺净退款后收入；不得为了本功能自动追溯扣除余额或修改支付状态。
- 被软删除的已用兑换码仍属于真实历史兑换，应按已有受邀用户范围读取该历史并计入；物理清除且无可靠快照的历史不能凭日志文字编造，显示可识别的覆盖范围限制。

## 接口与权限

- 新增登录态自助分页接口，例如 `GET /api/user/self/invitees?p=1&page_size=20&keyword=...`；服务端仅使用认证上下文 ID 作为 inviter_id，不接受客户端选择他人的 inviter_id。
- 服务端先取得当前权限快照，再仅选取本人的直接受邀用户，批量读取当前页对应用户的金额。分页与筛选不改变所有权校验。
- 无权限时只返回用户名、分页元数据和 `can_view_amounts=false`；不选择或序列化整张 User、不返回邮箱、手机号、令牌、余额、付款账户、兑换码明文、原始回调或订单支付标识。
- 已授权时返回最小聚合 DTO，不公开逐笔敏感支付信息；默认不开启下钻订单明细。
- 权限配置按一个整体保存，读取使用一致快照，适配现有 option 持久化/多实例同步机制；不要假定仅一台应用实例。撤销授权在每次后端请求生效，不依赖前端判断或旧权限缓存。
- 金额响应使用私有、禁止缓存策略，账号切换不得复用上一个账号的数据。结果分页按稳定排序返回。
- 只有 RootAuth 可修改该系统参数；普通用户即使构造 update-self 请求也不能授权自己。

## 实现约束与非目标

- 保留全部既有邀请奖励、个人返奖比例、充值/兑换/订阅幂等、用户额度和品牌；查询不能触发返奖、重置额度或重建邀请关系。
- 业务 JSON 使用 common 包封装，数据库代码兼容 SQLite / MySQL >=5.7.8 / PostgreSQL >=9.6，前端使用 Bun，七种已有前端语言保持可用。
- 不增加新的支付渠道，不修改网关认证规则，不将未验签数据作为实付依据。报告快照写入故障不应把成功支付变成失败或重复入账，应有可重试、幂等补录路径及报告不完整标识。
- 不查询生产数据、不修改生产配置、不自动部署。实施与测试使用隔离合成数据；验证完成另行交付发布方案。
- 不重新审计或修改此次 feature 范围之外的旧支付安全问题；发现阻塞本功能的问题应如实记录。

## 验收证据

1. 后端权限：off 默认、all、selected 命中/未命中、空名单、无效配置、撤销、身份伪造、其他人的邀约、普通用户尝试自授权；未授权响应中不存在任何金额字段。
2. 数据正确性：充值+兑换+订阅组合、订阅充值镜像去重、重复回调/兑换不重复、已用软删除兑换、失败/待支付排除、实付 0、历史未确认币种、不同币种分项、兑换配置变化后的快照保持、无限额兑换码无法折算提示。
3. 财务回归：统计前后用户余额、订阅已用额度及重置锚点、邀请关系和返奖不变；快照失败重试不重复入账/返奖。
4. 三种实际数据库上验证新增迁移及聚合结果；未实际覆盖的旧引擎版本明确记为兼容代码约束，不冒称实测。
5. 前端与真实浏览器：人数入口、空/加载/失败/分页/筛选、默认仅用户名、开启/关闭金额、指定用户选择保存与回显、撤销后清理、账号切换不复用敏感数据、窄屏及键盘操作。
6. 执行相关 Go 测试、必要 race 检查、前端测试/生产构建/i18n 检查；记录准确通过数量与外部支付未实测边界，不以合成网关冒充生产支付验收。
