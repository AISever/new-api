# 历史兑换码邀请返奖补发工具

用户要求处理兑换码返奖上线前已兑换、未返奖的记录，每个兑换码产生一条对应邀请人可见的日志。本次交付独立脚本及隔离验证，不执行生产补发，不发布新业务镜像。

## 现场只读核验

2026-11-02 生产仍为 `codex/invite+b77dd3008+production`，日志与业务数据同库。69 条已使用兑换码均早于新版本启动；其中 34 条具有有效直接邀请关系，涉及 2 位邀请人：额度码和订阅码各 17 条。未发现“邀请兑换返奖”日志，候选中无额度依据缺失、非正数额度、删除码或无效比例。

当前为比例返奖，默认比例 0.05，邀请方个人比例优先，个人 0 禁用。若按当前规则初步计算，候选奖励合计 165625000 个整数额度单位；这是只读预估，不代表已经发放，也不声称恢复了历史当时的比例或邀请关系。

## 处理方式

建议独立命令工具，使用已有 Go/GORM 及 JSON 包装函数，兼容 SQLite、MySQL 和 PostgreSQL。复用线上兑换返奖的计量规则，但不重新执行兑换履约。直接重新调用 Redeem 会拒绝已用码，批量修改余额则无法同时满足逐码去重和逐码日志要求，新增生产业务页面或重新发布应用也不是本次所需。

1. 默认只预览，输出受限权限的计划文件：固定兑换码 ID、已用状态、兑换时间、受邀用户/邀请人 ID、额度依据、采用比例、奖励额度及跳过理由。计划不包含完整兑换码、凭据或支付信息。明确指定历史截止点，排除新功能上线后的兑换。
2. 仅处理历史已成功兑换、尚未补发的码。额度码以已兑入额度为基数；订阅码以该次实际授予的订阅 amount_total 为基数，不按当前套餐标价、可用剩余额度或每日重置次数计算。依据缺失、无限额度、自邀、无有效邀请人或停用/删除邀请人均不臆造奖励。
3. 建议沿用预览时的现有比例规则（默认 5%，个人比例优先），精确十进制计算，逐码向零取整。历史没有比例/邀请关系快照，采用当前关系和当前规则必须在计划与操作说明中明确，不能标称历史规则还原。
4. 执行只接受经核对的固定计划及其哈希；全局规则、个人比例、邀请关系、兑换记录或额度依据变化时拒绝该计划，要求重新预览。执行前须有最新备份和恢复证明。
5. 以兑换码 ID 为永久唯一键建立独立补发记录。每码一个事务，锁定相关数据并重新核对；在同一事务内登记唯一补发记录、原子增加邀请方 aff_quota/aff_history、写入邀请方系统日志。重复执行、并发执行或崩溃重试不重复发放；日志写入失败则该码不发奖。补发记录独立于可清理的普通日志保存，不能只依赖日志文字去重。
6. 日志属于邀请人账号，显示“历史兑换返奖补发”、兑换码 ID、受邀用户名、奖励额度/系统币种显示和原兑换时间；不公开完整兑换码、账户隐私或受邀用户的充值明细。邀请人在现有“使用日志 → 系统”或“全部”中查看。此处是邀请人自己的收益日志，不开放邀请名单累计金额权限。
7. 跳过或异常码保留逐码管理员审计结果；没有有效邀请人的码不能凭空产生邀请人可见日志。若发现既有返奖/补发证据则不再发放，需核对不一致记录。生产当前同库，工具对独立日志库配置默认拒绝执行，避免跨库“发钱成功但日志失败”。
8. 仅新增补发账本/日志并增加受益邀请方的两个收益字段；不改钱包 quota、消费额度、兑换状态、订阅、fhy 131 锚点、系统配置或金额可见权限。不用旧数据库备份覆盖发布后的消费和充值。

## 隔离验证与交付

验证额度码、订阅码、个人比例/零比例、舍入、缺失依据、删除/停用账号、已发奖励排除、输入漂移、重复/并发执行、收益溢出、日志故障全事务回退、崩溃恢复及普通日志清理后仍不重复发放。SQLite 验证逻辑，PostgreSQL/MySQL 验证实际事务并发。使用现有用户日志接口验证日志归属与跨用户隔离，并在隔离测试页面实际查看日志。

交付工具、使用说明、预览结果摘要、测试证据及生产执行步骤；明确生产未执行。后续如用户要求正式补发，先核对最终清单和总额，再执行并审计每码唯一记录/收益增量/日志一致性。

用户已确认按当前规则补发。按此方案实现并在隔离环境验证；本轮不执行生产补发。当前规则是预览时的快照，并非恢复历史当时比例。
