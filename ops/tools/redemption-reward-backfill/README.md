# 历史兑换码邀请返奖补发

独立工具，不更新线上应用。默认生成预览，只有显式 `--apply` 和准确的计划 SHA256 才会发放。当前工作仅完成脚本和隔离验收，**未执行生产补发**。

使用当前规则：比例模式下默认比例、邀请人的个人比例优先（个人 0 禁用）。逐码计算实际授予额度 × 比例，精确十进制向零取整。额度码使用兑换额度；订阅码使用对应已授予订阅的 amount_total，不使用剩余额度、当前套餐价格或每日重置倍数。收益只增加邀请人的 aff_quota 和 aff_history。

每个成功补发的兑换码，在同一个事务中生成永久去重记录及邀请人的系统日志。邀请人进入 **使用日志 → 系统/全部**，可见兑换码 ID、受邀用户名、补发奖励及原兑换时间；不公开完整兑换码。跳过码及其原因留在预览中，无有效邀请人的码不凭空生成用户日志。金额查看权限保持不变，日志展示的是邀请人自己的收益。

## 本次固定范围

首次运行支持兑换返奖的生产镜像于 2026-11-02 11:24:50 北京时间启动。工具只接受截止秒数 `<=1793589890`（不含该秒），拒绝更晚的范围：新版本兑换奖励即使日志丢失，也不能被当作历史未发奖励再次发放。生产只读导出核对的 69 个已用码中，34 个符合当前规则，涉及 2 位邀请人，预估合计 165625000 个内部余额额度单位，按当前 500000 额度/美元换算为 **331.25 美元等值奖励**。这里按兑换授予的余额计算，不按 API 消耗的 Token 数计算。

历史没有当时比例/邀请关系快照，本工具采用预览时的当前规则和直接邀请关系，不能声称恢复历史当时规则。软删除的已用兑换码仍保留实际兑换事实，依据有效时纳入；删除/停用的邀请人不发放。若过去另有人工补发且未留逐码证据，须先人工排除/核对，不能仅凭“未找到日志”证明从未人工发放。

## 构建和预览

在项目根目录运行。Go 使用项目要求版本（go.mod），可通过 NEW_API_GO 指定。连接串仅从环境变量读取，不要放在命令参数、聊天或公共日志中。

```sh
# BACKFILL_DSN 应在受限环境文件或当前私有终端设置，示例不包含凭据。
# PostgreSQL / MySQL / SQLite 分别使用 --driver postgres / mysql / sqlite。
ops/tools/redemption-reward-backfill/run.sh \
  --driver postgres --before 1793589890 --out /private/reward-plan.json
```

本机可设置 `NEW_API_GO=/home/ctyun/.cache/new-api-security-toolchain/go/bin/go`。SQLite 只允许已经存在的文件，不会为预览创建数据库。独立日志库 LOG_SQL_DSN 非空时拒绝运行，避免跨库奖励与日志无法原子提交。

预览仅执行读取，不初始化应用、不迁移源表、不创建补发账本。生成全新 0600 文件，拒绝覆盖旧清单；摘要输出包含计划 SHA256、历史码数、待补发码数、总奖励额度及按系统币种换算的奖励显示金额。文件内含用户名/额度依据，仅限运维私有保存。逐码核对和汇总核对都应使用该文件。

工具也可单独构建，生产服务器无需 Go：

```sh
CGO_ENABLED=0 go build -trimpath -o /private/redemption-reward-backfill \
  ./ops/tools/redemption-reward-backfill
```

保持和预览相同的数据库地址、账号及 PostgreSQL 有效 schema。源表和已有账本必须位于 current_schema，不支持从 search_path 后续 schema 回退查找这些表，以免遗漏已有账本后再次返奖。计划绑定实际目标、schema、源表及内容；复制到另一个数据库的清单会被拒绝。隔离副本产生的预览不能直接用于生产，需在真实目标重新预览。

## 正式执行前提

1. 重新核验线上版本、全部应用副本/后台写入进程、运行配置及独立日志库状态，准备备份与隔离恢复环境。
2. **排空并停止全部应用写入者和副本后再执行。** 既有应用的部分路径使用先读后完整保存 User，仍运行时可能用旧行覆盖补发收益；仅靠工具事务无法保护这种应用级竞态。本工具不擅自停止线上服务，也不修改线上入口、镜像或配置；停写窗口需按已有验证过的维护流程执行，等待额度批量更新落库。
3. 确认批量更新落库、所有写入者已停止后，制作最终新备份并在隔离库恢复验证；在此停写窗口重新保存所有受益人两个收益字段及其他额度字段、配置、订阅（特别是 fhy 131）的正式审计基线，再生成最终生产预览。核对 34 个候选（若数量/比例/金额变化先查明原因），保留清单哈希；不能用停写前的备份或额度快照替代这一步。SQLite/MySQL/PostgreSQL 使用同库日志，MySQL 所有相关表必须为 InnoDB，否则执行前拒绝。只会新增专用账本，不迁移源表。
4. 最后由运维对已复核清单执行以下命令，不能将此 README 示例理解为本次已获准自动执行生产补发。

```sh
/private/redemption-reward-backfill --driver postgres \
  --apply /private/reward-plan.json --sha256 REVIEWED_PLAN_SHA256
```

无一键默认正式补发入口。钱包 quota、消费额度、兑换履约/状态、订阅及重置、配置均不由工具更新。原子日志与补发账本写入任一步骤失败，当前码的奖励全部回退；此前已提交码保持成功，返回报错码 ID，继续使用同一清单重试。不可用旧数据库覆盖恢复服务后的充值、消费等新交易，也不能盲目扣回可能已转入钱包的收益。

执行成功后，按每码账本和用户日志核对笔数、总额、邀请人收益增量，复核钱包/配置/订阅基线；确认后恢复原应用和入口并验证。期间出现异常，应保持其他写入者停止，先查清每码事务结果；同一清单重试安全，禁止重置账本来重发。首次确认完成后保留账本，普通日志被清理也不再发钱。
